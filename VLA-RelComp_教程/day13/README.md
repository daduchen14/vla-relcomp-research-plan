# Day 13：恢复率、配对检验、区间与失败边界

## 当日目标，以及为什么服务于 VLA-RelComp

把 pair/oracle 结果整理成四格原始计数、恢复率、damage 和置信区间；理解 McNemar/精确检验只看不一致配对。检查差异是否由单任务、单 seed 或单 init 驱动。

## 前置知识和开始前自检

理解 Wilson CI 和匹配 pair。自检：原失败 10 个中 oracle 恢复 4 个，分母是什么？原成功被破坏 2 个是否可忽略？独立比例检验为何浪费配对信息？

## 具体场景与最小例子

对同一 episode 条件比较 baseline/oracle：都失败、仅 oracle 成功、仅 baseline 成功、都成功。McNemar 关注中间两个不一致格；若仅 oracle 成功很多而反向很少，才支持有方向恢复。

## 零基础知识讲义

Recovery=`原失败且干预成功 / 原失败`；damage=`原成功且干预失败 / 原成功`。两者需同时报告。小样本应给原始四格、Wilson 区间和精确二项版 McNemar，而不是只报 p 值。P 值不等效应大小，也不证明因果前提。

稳定性审计按 task、seed、init 分层；若总体恢复全来自一项任务，结论应缩小为该任务条件。至少两个 seed 的要求是发现脆弱性，不是保证普遍性。

## 操作步骤、状态与预期输出

`实测`：运行 `analyze_registry.py`；再用 fixture 手工匹配 task/seed/init，确认 language oracle 是失败→成功、visual oracle 是失败保持失败但阶段改善。`待用户执行`：制作四格表和按 task/seed 分层表。`静态核验`：协议要求小样本报原始计数、CI 和精确检验。`估计—未运行`：真实至少两 seed 数据尚无。

变量实验：移除唯一恢复 pair，观察恢复率从 1/1 变无可估计，说明极小样本不稳定。预期任何除零都应明确 NA，不填 0。

## 在真实代码中的位置

episode registry 提供配对键；分析脚本只读原始 CSV，输出到 `reports/tables`。排除/修正必须生成新版本，不覆写原始行。

## 常见错误、诊断顺序、备用路线与止损

先核 pair key，再核缺失/异常，再列四格，再算率/区间，最后检验。分母错或把异常当失败先修 schema。统计排错 60 分钟；小样本不追求显著，报告边界。

## 时间预算、最低完成线、标准完成线与选做

正常 6–7.5 小时。最低：正确四格和恢复/damage。标准：按 task/seed 稳定性审计与反例。选做：手写精确二项尾概率并单测，不引入复杂统计包。
